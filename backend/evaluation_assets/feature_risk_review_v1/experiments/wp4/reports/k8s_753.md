# Feature Risk Review

- case_id: k8s_753
- Report completeness: FULL
- Risk Level: HIGH
- Priority: ACT_NOW

## Feature Summary

Introduces sidecar containers as init containers with a restartPolicy of Always, allowing them to start in order with other init containers, run for the pod's lifetime, and not block pod termination. Includes changes to resource calculation, kubectl output, termination behavior, and OOM score adjustment.

## Change Points

- New restartPolicy field on init containers to mark them as sidecar containers, with only 'Always' supported.
- Kubelet starts sidecar containers in order with init containers, waiting for startup completion (startup probe or postStart) rather than completion.
- Sidecar containers do not block pod completion; they are terminated when all regular containers complete.
- OOM score adjustment for sidecar containers is set to match or fall below regular containers to reduce OOM kills.
- Enable lifecycle handlers (postStart, preStop) and all probes (startup, readiness, liveness) for sidecar containers; readiness probes contribute to pod readiness.
- Resource calculation for scheduling and admission changes to account for sidecar containers running during init and regular phases.
- kubectl get pods output extended to include sidecar container status in READY column and init status.
- Termination behavior for sidecar containers: in alpha, terminated as regular containers; in beta, reverse-order termination after primary containers, with preStop hooks and SIGTERM handling.
- Topology and CPU managers need updates to handle sidecar container resource requests, especially for NUMA and CPU pinning.

## High-Risk Scenarios

- Enabling lifecycle handlers (postStart, preStop) and all probes (startup, readiness, liveness) for sidecar containers, with readiness probes contributing to pod readiness, changes probe execution and readiness semantics. This could affect pod readiness and lifecycle hook behavior, especially during startup and termination. [C1]
  - Risk area: Probe handling
  - Affected components: kubelet, Pod API
- Introducing a new restartPolicy field on init containers changes the API schema. Existing clients, controllers, and admission webhooks that do not recognize this field may reject or strip it, causing pods to fail or behave unexpectedly. The evidence notes that third-party controllers may strip the field, OPA rules may reject it, and backward compatibility is only guaranteed for pods not using the field. [C2]
  - Risk area: API compatibility
  - Affected components: kube-apiserver, Pod API, kubectl
- kubectl get pods output is extended to include sidecar container status in READY column and init status. This changes output compatibility and may confuse users who expect the previous format. The evidence shows the new output format. [C3]
  - Risk area: Output compatibility
  - Affected components: kubectl
- OOM score adjustment for sidecar containers is set to match or fall below regular containers to reduce OOM kills. This changes the OOM killer behavior, potentially affecting memory management and stability. The evidence mentions this intent to solve a specific issue. [C1]
  - Risk area: Memory management
  - Affected components: OOM killer, kubelet
- Resource calculation for scheduling and admission changes to account for sidecar containers running during init and regular phases. This affects scheduling accuracy and resource overcommitment, as sidecar resources are now considered in both phases. The evidence mentions this change in the proposal. [C1]
  - Risk area: Scheduling accuracy
  - Affected components: kube-scheduler, kube-apiserver, kubelet
- Sidecar containers do not block pod completion; they are terminated when all regular containers complete. This changes the lifecycle semantics for init containers, which previously had to complete before regular containers started. Workloads that depend on init containers running until pod completion may be affected. [C1]
  - Risk area: Container lifecycle
  - Affected components: kubelet, Job completion
- Sidecar containers start in order with init containers and wait for startup completion (startup probe or postStart) rather than completion. This changes the startup ordering semantics, potentially breaking workloads that assume init containers complete before any other container starts. The evidence describes the new startup condition and ordering. [C1]
  - Risk area: Startup ordering
  - Affected components: kubelet
- Termination behavior for sidecar containers changes: in alpha, terminated as regular containers; in beta, reverse-order termination after primary containers, with preStop hooks and SIGTERM handling. This affects graceful termination and lifecycle hook behavior, especially during pod termination. [C4]
  - Risk area: Graceful termination
  - Affected components: kubelet
- Topology and CPU managers need updates to handle sidecar container resource requests, especially for NUMA and CPU pinning. This affects resource allocation and NUMA awareness, potentially impacting performance and stability. [C1]
  - Risk area: NUMA awareness
  - Affected components: CPU manager, Memory manager, Topology manager

## Coverage Assessment

The existing test plan covers many key areas of the sidecar container feature, including lifecycle ordering, readiness probes, resource accounting, upgrade/downgrade behavior, and API server outage scenarios. However, there are notable gaps in coverage for OOM score adjustment, CPU manager and topology manager NUMA handling, kubectl output compatibility, and detailed termination behavior (especially preStop hooks and reverse-order termination). The plan also lacks explicit tests for scheduler admission control with sidecar resource requests and for memory manager behavior.

## Missing / Recommended Cases

Potential gaps:
- No explicit tests for OOM score adjustment of sidecar containers to ensure they are less likely to be OOM-killed than regular containers.
- No tests for CPU manager behavior with sidecar containers, especially CPU pinning and guaranteed QoS scenarios.
- No tests for Topology manager NUMA-aware resource allocation with sidecar containers.
- No tests for Memory manager behavior with sidecar containers, especially when memory requests are accounted during init and regular phases.
- No tests for kubectl get pods output to verify READY column and init status include sidecar containers correctly.
- No tests for termination behavior in beta: reverse-order termination after primary containers, preStop hooks, and SIGTERM handling.
- No tests for scheduler admission control to ensure sidecar resource requests are accounted for in scheduling decisions and LimitRanger defaults.
- No tests for resource overcommitment scenarios where sidecar containers run during init and regular phases, potentially causing overcommitment.
- No tests for probe execution and timeout handling for sidecar containers, especially startup probes and postStart hooks.
- No tests for lifecycle hook behavior (postStart, preStop) for sidecar containers, including failure scenarios.
- No tests for downgrade compatibility when feature gate is disabled after sidecar containers are in use, beyond rejection of new pods.
- No tests for API server down during sidecar container startup with readiness probes failing or succeeding.
- No tests for sidecar container restart behavior when kubelet restarts and containers are in various states (running, terminated, etc.).
- No tests for sidecar containers with multiple sidecars and complex ordering dependencies.
- No tests for sidecar containers with resource limits and QoS class assignment.
- No tests for sidecar containers with startup probes that fail and restart behavior.
- No tests for sidecar containers with preStop hooks during pod termination and graceful period.
- No tests for sidecar containers with readiness probes affecting endpoint readiness during termination.
- No tests for sidecar containers with liveness probes and restart policy Always.
- No tests for sidecar containers with postStart hooks that block startup and timeout handling.

Recommended missing cases (RECOMMENDATION, not existing tests):

- Add e2e_node tests for Topology manager with sidecar containers requesting resources on specific NUMA nodes.
- Add e2e_node tests for Memory manager with sidecar containers, verifying memory allocation and accounting during init and regular phases.

- Add e2e tests for resource overcommitment scenarios with sidecar containers running during init and regular phases.

- Add upgrade/downgrade tests to verify behavior when feature gate is disabled after sidecar containers are running, including pod status and termination.
- Add e2e tests for API server down during sidecar startup with readiness probes, verifying pod startup completes when API server returns.
- Add e2e tests for kubelet restart with sidecar containers in various states, verifying correct restart order and no duplicate starts.
- Add e2e tests for multiple sidecar containers with complex ordering and dependency scenarios.
- Add e2e tests for sidecar containers with resource limits and QoS class assignment, verifying admission and scheduling.
