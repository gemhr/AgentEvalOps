# Feature Risk Review

- case_id: k8s_1472
- Report completeness: FULL
- Risk Level: HIGH
- Priority: ACT_NOW

## Feature Summary

This feature introduces a new Kubernetes API type, CSIStorageCapacity, to expose storage capacity information from CSI drivers, and enhances the scheduler to use this information when making pod scheduling decisions for volumes with delayed binding or ephemeral inline volumes. The goal is to reduce the risk of scheduling pods onto nodes where volume creation will fail due to insufficient storage capacity. The feature includes a new field in CSIDriver.spec to opt-in, and extends the external-provisioner sidecar to gather and manage capacity data.

## Change Points

- New API type CSIStorageCapacity is introduced to store capacity information per storage class and topology segment.
- New boolean field 'storageCapacity' added to CSIDriver.spec to indicate driver support for capacity-aware scheduling.
- External-provisioner sidecar extended to gather capacity information from CSI drivers and create/update/delete CSIStorageCapacity objects.
- Kubernetes scheduler's CheckVolumeBinding function extended to filter nodes based on reported storage capacity.

## High-Risk Scenarios

- The external-provisioner sidecar is extended to create, update, and delete CSIStorageCapacity objects. This introduces risks of orphaned objects if the sidecar fails to clean up objects when drivers are removed or when storage classes change, leading to stale capacity information and potential scheduling errors. [C1]
  - Risk area: object lifecycle management
  - Affected components: external-provisioner, CSIStorageCapacity API, etcd
- The introduction of CSIStorageCapacity objects increases etcd storage overhead, as each object consumes storage and must be replicated. The number of objects can grow with the number of storage classes, topology segments, and drivers, potentially impacting etcd performance and cluster scalability. [C1]
  - Risk area: etcd storage overhead
  - Affected components: etcd, CSIStorageCapacity API
- The mutability of CSIDriver.spec.storageCapacity and the dynamic creation/update of CSIStorageCapacity objects introduce migration complexity for clusters upgrading from older Kubernetes versions or for CSI drivers transitioning to support capacity-aware scheduling. Operators may need to handle special cases during upgrades. [C2]
  - Risk area: migration complexity
  - Affected components: API server, CSIDriver API, CSI driver, external-provisioner
- The new CSIStorageCapacity API and the storageCapacity field in CSIDriver.spec introduce API compatibility risks. The field was initially immutable and later made mutable, which can cause issues for clients that assume immutability, and upgrades from older driver versions may require special handling. [C2]
  - Risk area: API compatibility
  - Affected components: API server, CSIDriver API, CSI driver
- The scheduler does not watch CSIStorageCapacity or CSIDriver.spec.storageCapacity changes, so pods blocked by lack of capacity may not be rescheduled promptly when capacity becomes available or when the driver disables capacity tracking. This can lead to delayed scheduling and inefficient resource utilization. [C3]
  - Risk area: scheduler performance
  - Affected components: kube-scheduler
- The scheduler only considers CSIStorageCapacity for unbound PVCs, not for already-bound PVCs. This can lead to suboptimal scheduling decisions during pod rescheduling (e.g., node drain), potentially placing pods on nodes where volumes cannot be rebuilt, affecting availability and performance. [C4]
  - Risk area: false scheduling decisions
  - Affected components: kube-scheduler
- The scheduler's CheckVolumeBinding function is extended to filter nodes based on reported storage capacity. This introduces risks of false scheduling decisions because the capacity information may be incomplete or inaccurate, and the scheduler may reject nodes that actually have sufficient capacity or accept nodes that do not. [C5]
  - Risk area: false scheduling decisions
  - Affected components: kube-scheduler

## Coverage Assessment

The existing test plan covers unit tests for scheduler scenarios (volume sizes/types, driver capacity tracking, topologies, node availability), external-provisioner unit tests (modes, storage classes, topologies, capacity info lifecycle), and end-to-end tests for RBAC and scheduling with CSI hostpath driver. However, it lacks explicit tests for API compatibility, etcd storage overhead, object lifecycle management (orphaned objects), and migration complexity.

## Missing / Recommended Cases

Potential gaps:
- No tests for API compatibility of new CSIStorageCapacity and CSIDriver fields across versions.
- No tests for etcd storage overhead or performance impact of many CSIStorageCapacity objects.
- No tests for orphaned CSIStorageCapacity objects when storage classes or drivers are deleted.
- No tests for migration from older versions or upgrade scenarios with alpha features.
- No tests for scheduler performance with large numbers of CSIStorageCapacity objects.
- No tests for false scheduling decisions due to stale or incorrect capacity data.
- No tests for RBAC rules beyond alpha deployment, e.g., permissions for external-provisioner to manage CSIStorageCapacity objects.

Recommended missing cases (RECOMMENDATION, not existing tests):
- Add API compatibility tests for CSIStorageCapacity and CSIDriver.spec.storageCapacity across Kubernetes versions.
- Add performance tests to measure etcd storage overhead and scheduler latency with many CSIStorageCapacity objects.
- Add lifecycle tests to verify cleanup of CSIStorageCapacity objects when storage classes or drivers are deleted.
- Add migration tests for upgrading clusters with alpha features enabled and verifying existing capacity data.
- Add scheduler tests with stale or outdated capacity information to ensure no false scheduling decisions.
- Add RBAC tests for external-provisioner permissions to create/update/delete CSIStorageCapacity objects in various namespaces.
- Add end-to-end tests for capacity-aware scheduling with multiple storage classes and topologies to verify correct node selection.
