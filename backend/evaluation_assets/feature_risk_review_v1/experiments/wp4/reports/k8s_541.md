# Feature Risk Review

- case_id: k8s_541
- Report completeness: FULL
- Risk Level: HIGH
- Priority: ACT_NOW

## Feature Summary

This feature introduces external credential providers for Kubernetes client authentication, allowing out-of-tree executables to supply credentials (bearer tokens or mTLS) via a new exec-based authentication flow. It defines configuration in kubeconfig, input/output formats (ExecCredential), caching behavior, and metrics for monitoring.

## Change Points

- New exec-based authentication flow in client libraries: before each request, the client executes a configured binary and uses its output for authentication.
- Addition of new configuration fields in kubeconfig (exec section) for users, including command, args, env, installHint, provideClusterInfo, and interactiveMode.
- New ExecCredential API (client.authentication.k8s.io/v1) with input and output formats, including spec.cluster for cluster information and status for credentials.
- Caching of provider response in-memory until expirationTimestamp; if no expiration, cache for client runtime.
- New metrics for exec plugin calls, certificate TTL, and rotation age.
- Deprecation of gcp and azure authentication options (keystone already deprecated).

## High-Risk Scenarios

- Caching of provider response in-memory until expirationTimestamp, or for the client runtime if no expiration is set, can lead to stale credentials being used if the expiration is not properly set or if the client runs for a long time. This could result in authentication failures or unauthorized access if credentials are revoked before expiration. [C1][C2]
  - Risk area: stale credentials
  - Affected components: client-go, authentication libraries
- Error handling for exec plugin execution is critical: if the binary is missing, fails to execute, or returns invalid output, the client must handle it gracefully. The installHint is provided for missing binaries, but other errors (e.g., invalid JSON, wrong API version) may not be well-handled, leading to authentication failures or crashes. [C3][C4]
  - Risk area: error handling
  - Affected components: client-go, authentication libraries
- Exec-based authentication executes an external binary before each request, which can introduce security risks if the binary path is untrusted or compromised. The binary has access to environment variables and potentially cluster information, and its output is used for authentication, making it a vector for credential theft or malicious actions. [C1][C3]
  - Risk area: security of credentials
  - Affected components: client-go, authentication libraries
- The new configuration fields in kubeconfig (exec section) introduce complexity and potential backward compatibility issues. Existing kubeconfig files that do not include these fields may behave differently, and the required interactiveMode field in newer API versions could break older plugins that do not set it. [C3][C4]
  - Risk area: backward compatibility
  - Affected components: kubeconfig, client-go
- Deprecation of gcp and azure authentication options (and keystone already deprecated) may break existing users who rely on these methods. The new exec-based flow may not be a drop-in replacement, requiring users to migrate to new configuration, which could cause authentication failures if not handled properly. [C1]
  - Risk area: backward compatibility
  - Affected components: kubeconfig, authentication libraries
- The ExecCredential API transmits sensitive fields such as token, clientKeyData, and clientCertificateData between the client and exec plugin. The evidence notes these should only be transmitted in-memory, but if the plugin is compromised or the communication channel is not secure, credentials could be exposed. [C2]
  - Risk area: security of credentials
  - Affected components: client-go, API group client.authentication.k8s.io
- The new metrics for exec plugin calls, certificate TTL, and rotation age may be incorrect if the exec plugin does not provide accurate expirationTimestamp or if the client caches credentials beyond the actual certificate validity. This could lead to misleading metrics and operational issues. [C2]
  - Risk area: metric correctness
  - Affected components: metrics system, client-go

## Coverage Assessment

The existing test plan covers key aspects of the exec-based authentication flow, including version mismatch detection, in-memory caching, single-flight behavior, timeouts, struct shadowing, helper methods, metrics, integration with shared informers, static auth interactions, and interactive login flows. However, the plan is high-level and lacks specific test cases for security, error handling, and backward compatibility. The absence of concrete test cases means the plan may not be fully implemented or validated.

## Missing / Recommended Cases

Potential gaps:
- Security of credentials: no explicit tests for credential handling in memory, output masking, or prevention of credential leakage in logs or error messages.
- Execution of external binaries: no tests for handling malicious or malformed executable output, command injection via args/env, or validation of executable path.
- Backward compatibility: no tests for existing kubeconfig files without exec sections, or for deprecated gcp/azure auth options still functioning.
- Error handling: no tests for non-zero exit codes, missing executable, permission denied, or malformed ExecCredential responses.
- Stale credentials: no tests for expirationTimestamp in the past, or for caching behavior when expiration is absent.
- Metric correctness: no tests for metric labels, values, or emission timing for exec plugin calls, certificate TTL, and rotation age.
- Interactive mode: no tests for all InteractiveMode values (Never, IfAvailable, Always) and their fallback behavior.
- Cluster information: no tests for provideClusterInfo=true and the content of spec.cluster, including CA data handling.
- Concurrency: no tests for concurrent requests with different exec configs or for single-flight behavior under high concurrency.
- Timeout: no tests for configurable timeout or for handling executables that hang indefinitely.

Recommended missing cases (RECOMMENDATION, not existing tests):
- Test that credentials are not logged or exposed in error messages or metrics.
- Test that executable output is validated against the ExecCredential schema and that invalid output is rejected.
- Test that command injection via args or env is not possible (e.g., using shell metacharacters).
- Test that deprecated gcp and azure auth options still work and produce deprecation warnings.
- Test that kubeconfig files without exec sections continue to work without regression.
- Test that non-zero exit codes from the executable result in clear errors and no credential caching.
- Test that missing executable or permission denied errors are handled gracefully and do not crash the client.
- Test that expirationTimestamp in the past causes immediate rotation and that no expiration leads to caching for the client runtime.
- Test that metrics for exec plugin calls, certificate TTL, and rotation age are emitted with correct labels and values.
- Test all InteractiveMode values (Never, IfAvailable, Always) and verify fallback behavior when TTY is not available.
- Test that provideClusterInfo=true populates spec.cluster correctly, including CA data and server address.
- Test that concurrent requests with different exec configs do not interfere and that single-flight works per config.
- Test that a configurable timeout is applied to executable calls and that hanging executables are killed.
- Test that transient failures during credential rotation are retried without hot-looping the executable.
- Test that static auth (basic, token, cert) can be combined with exec credential and that exec takes precedence when configured.
