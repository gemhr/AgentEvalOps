The harness needs two touchpoints with your loop, whatever it is built with: the **system context** in the prompt and a **turn boundary**. Attaching the read-only **task tools** is a third, optional one. No adapter required.

```python
from pandaprobe_harness import Harness, HarnessConfig

harness = Harness.create(HarnessConfig(repair_model="openai/gpt-..."))
```

`Harness.create()` provisions the workspace, wires every component (hook, mailbox, journal, rules, eval set, task tools, the repair agent), and schedules the startup health check.

<Warning>
  `repair_model` — or `HARNESS_REPAIR_MODEL` — is **required**. [The repair agent](/harness/loop/repair-agent) makes its own model calls, and no billable default is selected for you. Use `observe_only=True` to evaluate and journal without mutating anything.
</Warning>

It also accepts the two optional developer seams:

```python
harness = Harness.create(
    HarnessConfig.from_env(capture_eval_cases=True),
    replay=my_replay_fn,      # counterfactual rule validation + regression runs
    verifier=my_grader,       # ground-truth outcome, decides promotion
)
```

## 1. The system context

```python
system_prompt = harness.system_context(session_id) + MY_PROMPT
```

<Note>
  This is a **constant**: one sentence saying learned rules exist and naming the four read-only tools. No rule bodies, no scope index, no notice count — and building it reads nothing from the workspace. There is nothing to pre-select, because the agent conditions its own retrieval on the task with `harness_rules_search` and `harness_rules_read`.
</Note>

Because it never changes, a prompt fixed at construction time is as good as one rebuilt per turn. The `session_id` is required so the call shape stays uniform across integrations; `task_hint` is accepted and ignored.

## 2. The tools (optional)

```python
tools = my_tools + list(harness.task_tools.specs())
# on a harness tool call: result = await harness.task_tools.call(name, args)
```

Four read-only operations, or none — the loop works either way. Evaluation, notices, repair, and validation all run regardless; the tools only decide whether your agent can consult what was learned. `as_anthropic_tools`, `as_langchain_tools`, and `as_openai_function_tools` convert them to native formats — see [the task toolset](/harness/loop/agent-toolset#delivery).

<Note>
  Route every `harness_*` name to `harness.task_tools.call` rather than filtering names yourself. Enforcement lives in the dispatcher, so a hallucinated administrative call is rejected safely instead of reaching your domain executor.
</Note>

## 3. The turn boundary

<Warning>
  Delimit **turns**, not tasks. Score history is keyed per session, so a loop that fires turn-end once per task gives the [trajectory gate](/harness/loop/evaluation#the-trajectory-gate) exactly one sample per series — it can never reach `gate_window`, and nothing will ever fire. This is the easiest way to silently disable detection altogether.
</Warning>

Three equivalent styles — pick whichever fits your loop:

```python
# Async context manager (fires turn-end even on exceptions):
async with harness.turn(session_id):
    await my_agent_step(...)

# One-shot runner:
result = await harness.run_turn(session_id, my_agent_step, ...)

# Decorator:
step = harness.turn(session_id)(my_agent_step)
```

Or call the hook directly with a raw payload — the `end_state` you pass is what the [outcome verifier](/harness/closed-loop/outcome-verifier) receives *and* what a captured eval case carries as its replay input:

```python
harness.on_turn_end({
    "session_id": session_id,
    "turn_index": turn_index,
    "end_state": {"task_id": task_id, "task": user_input},
})
```

<Note>
  Use the **same session id** for the harness turn and the SDK trace context (`pandaprobe.session(session_id)`) — the evaluation scores whatever traces landed under that session.
</Note>

## 4. The barrier (recommended)

Turn-end is fire-and-forget by default. To make a lesson take effect *inside* the session, await the turn's evaluation and repair:

```python
async with harness.turn(session_id, settle=True):
    await my_agent_step(...)
```

or explicitly, when you want the diagnosis back:

```python
harness.on_turn_end({...})
result = await harness.settle(session_id)

if result.report is not None and result.report.gate_breached:
    for score in result.report.alerting_scores:
        log.info("tier %s %s=%.2f %s", score.tier, score.metric, score.value,
                 score.conditions)
if result.repair is not None:
    log.info("repair %s -> scope %s", result.repair.status, result.repair.selected_scope)
if result.timed_out:
    log.info("barrier expired; work continues detached")
```

`settle()` waits for the turn's evaluation, notice persistence, and one bounded [repair](/harness/loop/repair-agent) attempt. It deliberately does **not** wait for a validation round — a replay can need the very resource this turn holds, so awaiting it here could deadlock.

The barrier has its own generous budget (`barrier_timeout_s`, default `180s`), separate from `drain_timeout_s`. On expiry the work continues detached and `timed_out` is set — a slow platform costs you latency, never correctness.

<Note>
  **`settle()` consumes the turn's pending evaluation.** If you settle and then settle the *same* turn index again to fetch the report, the second call finds no new traces and returns an impoverished one. Take the report from the call that did the work.
</Note>

## Determinism helpers

Everything after `on_turn_end` is detached and non-blocking. When a test or script needs to observe results deterministically:

```python
await harness.refresh(session_id)          # join this session's in-flight evaluation
await harness.refresh_all()                # join every in-flight evaluation
drained = await harness.drain_validation(timeout=60)   # -> bool: did it finish?
settled = await harness.settle_validation(timeout=300) # run validation to a standstill
harness.hook.pending_sessions              # sessions with evaluation still in flight
harness.validation_pending                 # validation rounds still in flight
```

`refresh*` and `drain_validation` are bounded joins — correctness never depends on them; each background task handles its own result.

<Tip>
  **At a phase boundary** — before you archive a workspace, snapshot a ruleset, or report results — wait on `pending_sessions` **and** `validation_pending`, then call `settle_validation()`. Waiting on evaluations alone lets you snapshot while candidates are still being decided, which records a rule that had already earned promotion as permanently provisional. `drain_validation()` returns `False` when it gave up, so you can tell a completed drain from a timeout.
</Tip>

## Everything on the facade

| Surface | Purpose |
| --- | --- |
| `harness.system_context(session_id)` | The prompt preamble: one stable capability sentence. |
| `harness.task_tools` | The four read-only rule operations (`TaskToolset`). |
| `harness.turn(session_id, settle=False)` / `run_turn()` / `on_turn_end()` | Turn boundaries. |
| `harness.settle(session_id, timeout=None)` | The per-turn barrier → `SettleResult`, including `.repair`. |
| `harness.refresh()` / `refresh_all()` | Bounded best-effort joins on evaluation. |
| `harness.drain_validation(timeout=None)` | Join in-flight validation; returns whether it drained. |
| `harness.settle_validation(timeout=...)` / `harness.validation_pending` | Run validation to a standstill at a phase boundary; rounds still in flight. |
| `harness.validate_candidates()` | Run one candidate-validation round now. |
| `harness.run_regression(sample=None)` | Replay the eval set against the current rules. |
| `harness.mailbox` / `journal` / `rules` / `evalset` / `config` / `cli` / `filesystem` / `hook` / `adapter` | Direct store and hook access for inspection and scripting. |
| `harness.check_health()` | The memoized CLI/auth probe. |
