# WP4 Ground Truth Annotation Guide (Human Review)

本文件指导 **用户本人** 完成 5 个冻结 Case 的 Ground Truth 人工审核。Agent
（ZCode / DeepSeek）不得代替用户填写 `expected_*`，不得从 prediction / WP2 / WP3
artifact 反向生成 Ground Truth，不得把 `PENDING` 改为 `HUMAN_REVIEWED`。

## 1. 审核对象

冻结 Case 集合（必须且只能这 5 个）：

```text
k8s_541, k8s_753, k8s_1287, k8s_1472, k8s_1602
```

每个 Case 需要人工审核的 `expected_*` 字段：

```text
expected_change_points
expected_components
expected_risk_areas
expected_historical_issue_ids
expected_coverage_gaps
expected_risk_level
```

`expected_priority` 不存在，不要填写。

`expected_risk_level` 必须使用冻结量表：

```text
annotations/RISK_LEVEL_RUBRIC.v1.md
RUBRIC_ID = feature-risk-review-human-risk-level.v1
RUBRIC_STATUS = FROZEN_FOR_WP4_ANNOTATION
```

不得自行改写等级定义，也不得复用 WP3 runtime Risk Policy 作为 Ground Truth 量表。

## 2. 审核顺序（重要）

### 先看 source，不要看 prediction

只依据以下 source 判定 `expected_*`：

- `raw/kubernetes_enhancements/<case_id>/README.md`（KEP 原文）
- `raw/github_issues/enhancements_<kep_id>.json`（enhancement tracking issue）
- `retrieval/enrichment/kubernetes_kubernetes_issue_*`（真实历史 bug snapshot）
- `tests/test_plans.json`（已有 test plan）
- `cases/<case_id>/evaluation_reference.md`（该 Case 的参考材料）
- `cases/<case_id>/metadata.json`、`cases/<case_id>/source_manifest.json`

**不要查看**：

- `experiments/wp2_*`、`experiments/wp3_*` 输出
- 未来 `experiments/wp4/predictions/` 的模型输出
- 任何聚合 summary / RiskLevel / Priority 结果

不要先看 prediction 再反推 `expected_*`，也不要把 WP3 的
`k8s_541 = HIGH / ACT_NOW` 当作 Ground Truth。

### 填写内容

- `expected_change_points`：source 中确实发生的变更点；自由文本。
- `expected_components`：尽量使用 source 中的 canonical component 名
  （与 `FeatureChangePoint.affected_components` / top-level
  `affected_components` 对照时按冻结 normalization 比较：
  NFKC -> trim -> collapse whitespace -> casefold）。
- `expected_risk_areas`：source 支持的风险领域；自由文本。
- `expected_historical_issue_ids`：你判定真实相关的 historical issue 的
  stable ID（`github_enhancement_tracking_issue` 的 `source_id` 或
  `kubernetes_issue_snapshot` 的 `source_id`）。ID 格式要求：
  非空、无前后空白、仅 `[A-Za-z0-9_.:-]`。
- `expected_coverage_gaps`：现有测试覆盖不足之处；自由文本。
- `expected_risk_level`：只能是 `LOW / MEDIUM / HIGH`，或保持 `null`。
  必须严格按 `RISK_LEVEL_RUBRIC.v1.md` 的顺序与最低证据要求判断；只有 source
  能支撑该判定时才填写。
- `annotation_source`：一句话说明哪些 source document 支撑这份 Ground Truth，
  **不能**写 "generated by evaluator"。

### 字段状态（`annotations/field_status.v1.json`）

对每个 `expected_*` 字段：

- 如果你审核了该字段并愿意作为 Ground Truth 使用：`EVALUATED`。
- 如果该字段无法可靠标注：`NOT_EVALUATED` 并在 `reason` 说明原因。

字段标为 `NOT_EVALUATED` 时，该字段不进入 quality metric denominator。

### PENDING empty vs 人工确认空

`expected_* = []` 且 `annotation_status = PENDING` **不等于** 人工确认空。
只有 `annotation_status = HUMAN_REVIEWED` 且该字段 status = `EVALUATED`
且列表为空，才是 "human-reviewed empty Ground Truth"。

## 3. 完成审核后

1. 在 `annotations/annotations.v1.json` 把该 Case 的 `annotation_status`
   改为 `HUMAN_REVIEWED`（Agent 不代改）。
2. 更新 `annotations/field_status.v1.json` 中该 Case 各字段为
   `EVALUATED`（或保留 `NOT_EVALUATED` + reason）。
3. 对 `expected_risk_level`，确认 `annotation_source` 已记录量表要求的 source、
   影响链、缓解/测试证据和相邻等级排除理由。
4. 运行：

```text
cd backend
uv run python scripts/run_feature_risk_review_evaluation.py validate-annotations
```

5. 确认 `GROUND_TRUTH_STATE = GROUND_TRUTH_READY`。
6. 运行 `prepare-manifest` 冻结 annotation digest 与 runtime manifest：

```text
uv run python scripts/run_feature_risk_review_evaluation.py prepare-manifest
```

7. 确认 `FREEZE_STATUS = FROZEN` 后，才允许后续真实 one-pass execution。

## 4. 真实 run 之后的人工 adjudication（本阶段不做）

真实 prediction 落盘后，用户仍需完成（Agent 不代填 verdict）：

- Change Point / Risk Area / Coverage Gap 的 1:1 match table
  （`MATCH / NO_MATCH`），写入 `experiments/wp4/adjudications/<case_id>.json`。
- Citation rubric（`SUPPORTED / PARTIALLY_SUPPORTED / UNSUPPORTED /
  UNVERIFIABLE`），按 `RiskFinding <-> EvidenceRef` pair 逐条判定。

所有 verdict 必须写入 adjudication JSON，不能只手工看完后直接填 summary。
